HILT — Project Overview¶

Philosophy: "The act of running a HILT Test is the act of producing irrefutable evidence."

"Happy path" scripts work 99% of the time but cause 100% of the line stoppages because they fail ambiguously. HILT forces the SE to handle the "Sad Path" (Infra vs. Hardware vs. Integration) at design time.

What It Is¶

An opinionated manufacturing test framework built in Python (asyncio). It seeks to implement empathetic architecture by addressing SE → tech communication issues upstream via a pit-of-success model.

This is the Python port of the TypeScript original (../hilt-test-legacy/, read-only reference). Parity with the original is explicitly not a goal; the contracts are carried forward, the enforcement is stronger.

How it does that¶

HILT gives the SEs a framework that allows them to focus on getting the test right and logging meaningful evidence. It does this by reducing cognitive load on the SE as much as it possibly can. The SE declares their intent and HILT collects and organizes structured evidence. Much like a real hilt test, the act of executing the test is the act of producing evidence. full stop. The SEs capture meaningful information, and the hilt inspector guarantees that a tech is able to turn that data into information at 2am.

The HILT Success Metric¶

A Floor Technician (the "FT" of the source docstrings) can accurately categorize a failure and initiate the correct recovery protocol within 60 seconds of opening the Inspector, without needing to Slack the Software Engineer.

The Core Purpose¶

"We are giving developers the tools they need to give floor operators the tools THEY need, and doing so without additional cognitive load on the developer."

Two-level service contract: 1. Framework → Developer: lifecycle guarantees, automatic evidence collection, structured failure signals — developer focuses on test logic, not plumbing. 2. Developer → Floor Technician: clear names, hardware-domain failure messages, scoped artifacts in the inspector tree — tech makes confident judgment calls without escalating to a software engineer.

The Primary Beneficiary: Floor Technician¶

"Floor technicians simultaneously have the biggest impact on the success of our business, and the least control over how it operates"¶

Typically early-career technology enthusiast. Passionate, capable, but may be operating at the edge of their knowledge. They are the first person to see failures and to make failure category judgment calls. They are the experts on how to handle any given failure mode. The inspector is their primary tool — and also a containment layer preventing them from going places they shouldn't. The station page is docs/floor-technician.md (Floor Technician guide): how to read result.json and what to do next, without opening the suite source.

The Atom¶

TestComponent is the irreducible unit of the manufacturing test problem domain.

  • Does not know or care what the DUT is
  • Does not know what stage it's running at
  • Does not know what surrounds it in the composition
  • Only knows: configure → build_suite → cleanup

A rack-level L11 test is not a different kind of thing — it is more atoms composed together. Leaves, sequences, parallel nodes, and full hardware devices are all instances of TestComponent; the framework is fractal. A TestComponent is simultaneously a claim about hardware and a procedure for verifying that claim: evidence at scale N−1 becomes a verdict at scale N. The DUT tree and the test tree are one structure.

The Chemistry Mental Model¶

Level Framework Construct
Atom TestComponent (leaf via self.test())
Molecule self.sequence() (ordered, bails on failure), self.parallel() (concurrent, collects all)
Organelle TestComponent subclass (encapsulates state + lifecycle, produces atoms via build_suite())
Organism Full rack/system-level suite
Emulsion L10+JBOG/JBOD — two molecules behaving as unified system under test

Key property: No level needs to know about the levels above it. Composition is the only coupling mechanism and the framework is contractually obligated to provide it.

The Three Terminal States¶

Every run of a TestComponent resolves to one of three peer states — no silent exits, no hidden fourth category:

  1. Pass — the test method returned PASS explicitly, bare or as PASS(evidence) carrying its readings. Cannot accidentally pass: the framework checks isinstance(result, Verdict), and a Verdict is only obtained by importing PASS or calling it, so a string, a truthy value, or a parsed config cannot forge it. A method that declares its evidence with @evidence(...) cannot pass without carrying it.
  2. Fail — the test method raised a TestFailure. Structured articulation of what the hardware did wrong, or (for a plain exception) a loud contract violation signal that the developer didn't model this failure mode.
  3. Aborted — no verdict was produced. Two causes:
  4. Harness-level: an external integration hook (before_each/after_each on the run params) threw, halting the run before a verdict could be reached.
  5. Node-local: the test method returned anything other than the PASS sentinel — a None fall-through or an explicit wrong value (the string "PASS" included). No verdict exists, so the framework refuses to forge Fail (or Pass) on its behalf. Siblings are unaffected.

Peer state to Pass/Fail, NOT a flavor of failure.

The node-local Aborted cause is a deliberate deviation from the TypeScript original, which folded a missing verdict into the contract violation/Fail path. The port's position: a contract violation that threw produced information (Fail + violation signal); a method that returned wrong produced nothing, and reporting nothing as a verdict would itself be a quiet lie.

The tech's recovery protocol differs for each. A Fail says "check the hardware." An Aborted says "check the harness — the shop-floor DB, the coordinator, the integration layer — or the test method that produced no verdict — not the unit." Collapsing these into one category is exactly what the framework refuses to do.

A two-layer bug-guard exists alongside the three terminal states: - ContractViolation — developer contract violation, raised at the lifecycle layer - FrameworkContractViolation — framework internal contract violated (should be unreachable, indicates a bug in the framework itself)

Failure Taxonomy¶

Root causes the framework must make obvious: 1. DUT failed a check — TestFailure from a test method or from configure() → state Fail. A TestFailure from configure() means "the device did not reach a testable state"; whether hardware or infrastructure is the cause is not knowable from code — the human triager decides. 2. Hardware lying — survey artifacts expose mismatch (claimed success vs actual state) 3. Test method contract violation — plain exception from a test method or from configure() → violation signal 4. Integration failure — ExternalIntegrationFailure from before_each/after_each aborts the run. The test may be fine; the harness around it broke (e.g. shopfloor DB unreachable, network congestion). 5. Operator interrupt — OperatorInterrupt from SIGINT/SIGTERM during a live run. The Floor Technician reads that the operator stopped the rack, not that the harness or the DUT failed.

A human must always make the final determination. The framework presents evidence clearly enough that the tech can make the call without a software engineer's help.

The Temporal Backbone¶

The log artifact is the authoritative chronological record of a test run. Two complementary views: - Structural (inspector tree): what ran, what passed, what failed, how tests compose - Temporal (log backbone): what happened, in what order, what state at each moment

await utils.capture_artifact(artifact) stitches artifacts onto the timeline via structured pointer log entries. The public Artifact value has no file-writing method, so the framework cannot persist evidence without also recording that pointer.

Every full run creates one timestamped directory beneath the configured artifact root. Logging nodes stream a human timeline.log and a versioned Inspector timeline.jsonl; leaves roll into their nearest owning ancestor. Both views are flushed entry by entry, preserving the accepted chronology through interruption. When the root reaches Pass, Fail, or Aborted, the framework atomically writes its versioned RunResult to result.json at that run-directory root. The root timeline's final entry points to the file, so the structural and temporal views remain joined.

Timestamp integrity is a system requirement. NTP sync on the test host is not optional. The log backbone is used as a legal instrument in customer disputes ("did failures start before your 2pm firmware push?").

Integration Hooks: The External-World Contract¶

before_each and after_each on the run params are how HILT composes with the world outside the test framework — shop-floor databases, lab coordinators, audit pipelines, any system that needs a "started" signal before each test and a "finished" signal after.

  • Registered once at the root run() call, fire around every executed test in the tree (fractal dispatch)
  • Throw from either hook → run halts → enclosing node transitions to Aborted
  • Pair invariant: after_each fires even when before_each threw, so "started" and "finished" records stay balanced in the external system. No orphan rows.
  • Hooks receive a narrow context (node name, ancestor chain, scoped logger, env snapshot) — NOT utils.exec or get_shell. The interface encodes "integration hooks don't touch the hardware."

When a hook throws, the required end state is for the framework to close every in-flight transport across the whole tree immediately (SSH connections destroyed, subprocesses killed). A 30-minute firmware flash in flight when the integration layer halts must NOT continue to mutate the hardware. This is load-bearing for manufacturing test integrity.

The Pit of Success Model¶

The correct pattern must be the path of least resistance — enforced by API shape, not documentation.

HILT is deliberately designed so that the right way to write a test is also the easiest way. The framework uses runtime enforcement, import-time structural checks, sensible defaults, and loud signals to guide developers toward honest, evidence-rich tests without requiring them to constantly consult the docs.

Here are some of the ways HILT implements this:

  • No pass by default — test methods must explicitly return PASS, or PASS(evidence) with the readings that prove it. Reaching the end of the method without doing so is a missing verdict (node-local Aborted); raising a plain exception is a developer contract violation. A method that declares its evidence with @evidence(...) cannot pass without carrying it. Even internal implementations like TestSequence explicitly model the passing condition as (all tests ran AND all tests passed) — it does not silently pass if nothing threw.
  • Setup is constrained to configure() — All infrastructure wiring, readiness checks, and context creation must happen in configure(). The framework merges the return value into utils.ctx for the rest of the lifecycle and all descendants, and ctx is read-only from then on: inputs come in through configure, readings go out with the verdict. This prevents hidden state coupling and makes the data flow explicit.
  • Unmodeled failure modes are loud — Raising anything other than a TestFailure (or subclass) from a test method produces a clear "CONTRACT VIOLATION" message. The framework refuses to let an unhandled error silently become a pass.
  • use_shell() auto-wires execution routing — Calling utils.use_shell() in configure() automatically rebinds utils.exec to route through the SSH connection. Child tests and descendants inherit the routing with zero extra code. The SE never has to manually thread SSH interfaces.
  • Composition takes bound methods directly — self.test("name", self._my_method) works with a plain bound method reference. No wrapping, no binding ceremony.
  • Sensible defaults reduce boilerplate — self.test("name", self._my_method) defaults to discrete_log_file=False, so its logs automatically roll up into the parent. This gives you one log per logical abstraction instead of one log per screw.
  • Survey and audit hooks belong in the constructor — Registering them only in __init__ makes them part of the test's stable identity (visible on the class and consistent across runs).
  • wait_for() requires intent — The looking_for parameter is mandatory and becomes the primary diagnostic string when a timeout occurs. This nudges developers to write human-readable failure messages.
  • Import-time structural enforcement — a tier the TypeScript original never had. __init_subclass__ on TestComponent verifies at class definition (import time, before any hardware is touched) that the subclass is structurally sound: required lifecycle methods present and async, sealed internals (main, run, _run_lifecycle, the _safe_* family) not overridden. A malformed test refuses to import; it can never reach the floor.

These constraints are not restrictions — they are guardrails that make it difficult to write ambiguous or incomplete tests while making the correct patterns feel natural.

Why HILT Rejects "Pass by Default"¶

Most test frameworks treat "the test reached the end without throwing an error" as a passing result. This is the default mental model the industry has used for decades.

HILT rejects it outright.

The Quiet Lie¶

When a test passes by default, it has only proven one thing:

It did not encounter any of the failure modes the author happened to think of and write explicit checks for.

That is not evidence that the system works. It is a quiet lie — one that accumulates silently until it causes a line stoppage. HILT provides the guardrails that make it difficult to accidentally ship a test that only appears complete. The same conviction governs what a pass carries: a pass without its declared evidence is not a pass.

Cases Where Explicit Pass Modeling Feels Awkward¶

Here are the situations where forcing an explicit PASS can feel clunky if you are coming from a pass-by-default mentality. In every case below, the job is the same: make the pass condition a readable check the next developer can find and understand. return PASS on its own is syntax, not modeling — the conditional that gates it is where your intent lives, and where hilt-check (the static-analysis tier) will insist it goes.

Situation Why It Feels Awkward How to Model the Pass Condition
Long-running / soak tests Success = "it didn't crash for 8 hours" Track error count or health samples across the run. if errors == 0 and samples_collected >= expected: return PASS — the conditional names what "healthy for 8 hours" actually means.
Event-driven / callback tests Success depends on receiving a callback within time if await wait_for(lambda: callback_fired, looking_for=...): return PASS — the wait returning truthy IS the success condition, gated explicitly.
Performance / load tests Success = "p99 latency < 50ms and throughput > 10k req/s" Collect metrics, then: if metrics.p99 < 50 and metrics.throughput > 10_000: return PASS — both thresholds named in code, not just in your head.
Fuzzing / property-based tests Success is probabilistic ("no counterexample found in 10,000 runs") if iterations_completed == 10_000 and not counterexamples: return PASS — both halves matter: you ran the full budget AND found nothing.
Best-effort / smoke tests "It's okay if some optional checks fail" Define the threshold as a variable then if critical_checks_passed: return PASS. The next reader sees the threshold immediately.
Non-deterministic external systems Success depends on flaky third-party behavior After retries: if last_attempt_succeeded: return PASS. The retry loop models the flake tolerance; the final conditional models the verdict.

Why This Matters to Floor Technicians¶

Floor Technicians are the primary consumers of everything you produce. They are the ones who will open the Inspector at 2am when a station is down. They need to answer three questions in under 60 seconds:

  1. What actually happened?
  2. Is this a hardware problem, a test problem, or an infrastructure problem?
  3. What should I do next?

Pass-by-default tests make all three questions harder. The tech is left guessing at your intent, debugging ambiguous results, and sometimes having to escalate because the evidence is unclear.

HILT is built so that the evidence a tech needs is produced automatically and presented clearly — without requiring them to read your source code or understand your design intent.

What HILT Demands¶

The three-tier enforcement stack¶

HILT does not merely prefer explicit passes — it rejects implicit ones at every tier of the enforcement stack:

Tier Mechanism Enforces
1 Runtime IoC wrapping (the child-boundary in lifecycle.py) Verdict contract, failure taxonomy, lifecycle order — can never be bypassed
2 Import-time structural checks (__init_subclass__) Subclass shape, sealed internals — fires before hardware is touched
3 Static analysis (hilt-check) Declarative syntax: pure build_suite, gated PASS, immutable-self idiom

Rule: nothing that protects hardware or verdict integrity may live only in tier 3.

  • In the runtime contract: test methods must return the PASS sentinel explicitly. Reaching the end without doing so produces no verdict — the node renders Aborted, never Pass.
  • In internal implementations: even when all conditions are met (as in TestSequence), the framework still performs an explicit check and refuses to silently pass.
  • At the static-analysis level: returning PASS outside of an if condition is surfaced as a lint error — the framework wants you to model your success condition deliberately.

This is more work up front. It forces you to think about what "success" actually looks like with the same rigor you apply to failure modes.

In return, you get tests that mean what they say, clear failure categorization, and automatic structured evidence that a floor technician can trust.

Where things live¶

The concepts above are carried by the modules under src/hilt. Each line says what the module is for, not what it contains; the contracts themselves are stated once, in contracts.md and the pages linked from it.

Module What it is for
__init__.py The public surface: hilt.__all__ is the documented API (api.md); every other name in the package is internal.
base.py The atom: TestComponent, the one node every suite is composed from, and the framework-owned lifecycle that runs it.
lifecycle.py Tier 1, the kernel of trust: the child boundary that turns what a test method returns into one of the three terminal states.
verdict.py The non-forgeable PASS sentinel and the Verdict a test method hands back.
errors.py The failure taxonomy: which exception means Fail, which means Aborted, and who is being told.
utils.py The per-node surface authored code is handed: exec, ctx, env, logging, measurements, hook registration.
evidence.py @evidence: the readings a test method promises to carry with its PASS.
measurement.py Parametric measurements: a number with a unit and limits, recorded beside the verdict (measurements.md).
run_data.py The JSON-safe view of ctx and verdict evidence that reaches the run record.
results.py The immutable evidence of a run and its JSON boundary to the Inspector (inspector-json.md).
timeline.py The temporal backbone: the durable per-node records that are a run's authoritative chronology.
artifacts.py Point-in-time captures and their framework-owned persistence.
hooks.py The integration hooks (surveys, audits, before_each/after_each) and the deliberately narrow contexts they see.
executor.py The host-side execution choke point every blocking call passes through.
routing.py Topology-aware exec routing: which hop a node's utils.exec travels through.
remote.py The remote transport contract the concrete transports implement.
ssh.py The SSH transport.
mock.py The in-process transport for self-tests: no hardware, no SSH.
arp.py MAC-to-IP resolution over the node's current exec route.
device_api.py The Device API (CoAP/HTTP) contract: resource requests, not an exec subclass (hil/device-api.md).
junit.py The JUnit XML reporter over the run record, for CI systems that read that format (junit-xml.md).
cli.py The hilt command line: run, new, inspect (hilt-run.md, hilt-new.md, inspector.md).
scaffold.py Writes a gated-PASS suite and its self-test from a class name, so a new suite starts inside the pit of success.
inspector_*.py (ten modules) The Floor Technician's Inspector, split reader / model / view. Readers (inspector_json, inspector_run, inspector_timeline, inspector_artifacts) load saved evidence and execute nothing; models (inspector_tree, inspector_selection, inspector_artifact_navigation) turn it into rows and cursors; views (inspector_timeline_view, inspector_artifact_view, inspector_app) render and forward keys, deciding nothing.
